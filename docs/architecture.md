# Стек и архитектура решения

**Задача:** раннее (за 10–15 мин) прогнозирование отклонения от графика наземного транспорта
по потоковой телематрии NDTP + диспетчерский BI-дашборд.
Хакатон Московского транспорта, максимум 36 баллов на этапах 1–2.

Все числа ниже — результат аудита реальных данных из репозитория, а не предположения.

---

## 0. Краткий ответ

| Вопрос | Ответ |
|---|---|
| Стек | Go (весь онлайн-контур) + Python 3.12 (ML) + React/TypeScript (дашборд), без базы данных в онлайн-контуре |
| NDTP-парсер | **Go**, `encoding/binary` + собственная реализация CRC-16/Modbus в пакете `ndtp` (`hash/crc16` отсутствует в этой сборке Go). Python отпадает: библиотек нет, писать вручную на `struct` — тот же объём кода без выигрыша |
| Модель | CatBoost (MAE-objective) на дельте `target − cur_dev_s`, ансамбль с PyTorch temporal encoder, экспорт в ONNX |
| Реалистичная цель | критерий 1: 4–5 из 6 баллов; критерии 2–5: по полной |

## 1. Результаты аудита данных

### 1.1. Утечка в раздаче (используется только как локальный оракул)

| Проверка | Результат |
|---|---|
| `md5sum test/traffic.csv validate/traffic.csv` | **совпадают** (`7c59b911c7ec057dc589fb594299378b`) |
| `validate/schedule_plan.csv` vs `test/schedule.csv` | та же последовательность из 5558 строк, отличается только отсутствием `time_fact_begin` |
| `target_stop_id` из `validate/points.csv`, найденные в `test/schedule.csv` | **151 из 151 (100 %)** |
| Значит, ground truth для всех 151 точки validate восстанавливается точно | да |

**Решение:** оракул используется **исключительно** в `scripts/oracle_audit.py` для честного измерения MAE на validate в ходе разработки. В prediction-path не попадает. Факт обнаружения описывается открыто в `docs/data-audit.md` и README — это демонстрирует глубину разбора данных, а не эксплуатацию дыры.

### 1.2. Метрика и реальные пороги баллов

```
mae_zero (validate)                  = 108.13 с
MAE при pred = cur_dev_s (baseline)  =  88.72 с  →  score = 0.18
```

README утверждает, что baseline даёт ≈ 0.40 — это **неверно** (проверено на данных).

Поскольку на validate `mae_zero = 108.13`, а формула
`score = max(0, min(1, (mae_zero − MAE) / (mae_zero − MAE_TARGET)))` даёт
`score = 1 − MAE / mae_zero` при любом `MAE_TARGET ≤ 32`, получаем пороги:

| Баллы | Требуемый MAE |
|---|---|
| 6 | **≤ 32.4 с** |
| 5 | ≤ 43.3 с |
| 4 | ≤ 54.1 с |
| 3 (baseline) | ≤ 65 с |

Отсюда проектируется вся работа по качеству модели.

## 3. NDTP-парсер: почему Go, а не Python

### Решение: писать на Go.

**1. Нулевая выгода от Python.** Библиотек парсинга NDTP не существует ни в одной экосистеме.
Формат по спеке: packed little-endian структуры без выравнивания, CRC-16/Modbus
(`poly 0xA001`, `init 0xFFFF`) с переставленными байтами в NPL, диспетчеризация по типу ячейки.
В Go это `encoding/binary` + `switch` по типу — около 250 строк на все используемые ячейки
(`Nav00`, `IntSensor02`, `Usi08`, `Can10`, `Termo16`, `Lls15`).
В Python придётся писать то же самое руками на `struct.unpack` + собственный мини-фреймворк.
Объём кода сопоставим, скорость и предсказуемость — нет.

**2. Модель конкурентности.** Спека §4: на каждый `unitId` — отдельное TCP-соединение,
с handshake, reconnect и пропуском тиков при занятом сокете. На демо 30 ТС, в реальной
эксплуатации — сотни и тысячи. Go (goroutine + `bufio.Reader`) держит десятки тысяч соединений
в единицах мегабайт. Python потребует asyncio + `uvloop` + ручного пула, и всё равно упрётся
в GIL на сериализации.

**3. p99 без настроек — это баллы по критерию 5.** Паузы Python-GC видны на дашборде,
и жюри их заметят. Go даёт предсказуемый хвост из коробки.

**4. Один бинарник = один маленький образ.** Статическая линковка, `FROM scratch`,
холодный старт < 1 с. Критерий 5 прямо снижает балл при непредсказуемом старте контейнеров.

**5. Train/serve skew исключается по построению — там, где он вообще исключаем.**
Один код считает признаки и для онлайна, и для офлайна: `internal/features`
вызывается и конвейером `serve`, и командой `transportctl replay` на
исторических CSV. Расхождение *между этими двумя путями* исключено по
построению, и это проверяется golden-тестом
`internal/pipeline/TestOnlineAndOfflineAgree`.

Но нулевое расхождение **с обучающей выборкой** недостижимо, и это не мнение,
а измерение: эталонная подсказка `cur_dev_s` в 43.6 % меток опирается на
фактическое прибытие, наступающее **после** момента прогноза `T`. Подробности и
числа — в [ADR 0004](adr/0004-cur-dev-leak-and-skew.md). На питче это
формулируется честно: расхождение измерено и названо, а не объявлено
отсутствующим.

**6. Тестируемость бинарного протокола.** Единственно надёжный тест — golden-файлы:
снять реальные пакеты эмулятора в `.bin`, затем `Decode(golden) == expected struct`
плюс тесты на каждый тип ячейки и на битый CRC.

### Честная оговорка и компромисс

Риск не в языке, а в том, что feature engineering на Go итерируется медленнее, чем в pandas.
Поэтому деление обязанностей сделано так, чтобы **критерий 3 закрывался буквально**,
а тяжёлая статистика оставалась в привычной среде.

**Go считает (это перечислено в критерии 3):**
- отклонение от графика на текущий момент `cur_dev_s` — детекция прибытий + сопоставление с планом;
- средняя скорость на сегменте;
- время простоя (текущий простой, последний, скользящий);
- `distance_to_target` вдоль маршрута, `stops_remaining`, `heading_error`, `staleness`, `location_valid_ratio`.

**Python строит поверх окна (ОДНА функция `features()` для train и serve):**
- rolling-статистики скорости и простоя на 1/3/5/10 минут;
- скорость ТС в процентах от исторического профиля участка в это время суток;
- межмашинные агрегаты (средняя скорость ТС на том же участке маршрута);
- тренды и импульсы.

На проводе едут **только 21 признак из `features/v1.yaml`**, без сырой
телеметрии. Это не экономия на размере запроса: утечка `cur_dev_s` из
разданного окна была найдена именно в нём (ADR 0004), и любое окно на проводе
приглашает вернуть её обратно. Окно остаётся в Go, в Python попадает
`features()` поверх уже посчитанных значений, и обе стороны сверяют список
имён.

### Контракт признаков

`features/v1.yaml` — имя, тип, порядок, null-семантика, единицы измерения.
Go реализует и выгружает; Python при загрузке модели сверяет список имён и падает при расхождении.
Golden-тест (планируется): офлайн-выгрузка на `train/` должна давать parquet,
на котором обучалась модель, — тогда фичи train и serve тождественны по
построению. Пакет `features` в `transportctl` ещё не реализован, поэтому
сейчас это требование не проверяется автоматически.

### 4.1. End-to-end поток (критерий 3)

```
NDTP-пакет
  → декодер (NPL/NPH/CRC/ячейки)
  → ring buffer ТС
  → детекция простоя + прибытия на остановку
  → сопоставление с плановым расписанием (рейс, направление)
  → отклонение + скорость сегмента + время простоя ─┐
                                                     ├→ FeatureFrame
признаки 21 шт. из features/v1.yaml ─────────────────┘
  → ограниченная очередь → ML Core (CatBoost)
  → delta_s, p_late, model_version   (при недоступности: кэш, затем baseline)
  → порог: predicted ≥ 120 с ∧ горизонт ∈ (10; 15] мин  → ИНЦИДЕНТ
  → гейтвей: REST + WebSocket broadcast
  → цвет на карте (зелёный/жёлтый/красный) + карточка инцидента у диспетчера
```

Поток реализован пакетом `internal/pipeline`: он единственный владелец разбора
пакетов, накопления состояния, привязки `unit_id → tr_id` и выбора окна
расписания. Команда `serve` не содержит логики прогноза — она поднимает сервер
и конвейер, чтобы нельзя было запустить одно без другого.

Прогноз — не следствие пакета, а решение по таймеру (`--tick`, по умолчанию
15 с). Пакеты приходят каждые 10 с, и кадр на каждой точке отправлял бы в
модель одно и то же прогнозное событие.

Тик проверяет наступление границы, а не строит кадр. Момент прогноза `T`
лежит на сетке в пять минут (`--grid`) и округляется вниз, потому что модель
обучалась на выборке с такой сеткой; между границами новой информации для
прогноза на двадцать минут вперёд нет. Данные кадра ограничены `T` с обеих
сторон — по времени события и по времени приёма, — иначе кадр, подписанный
`08:05`, получил бы состояние машины от `08:07`. Машина, включившаяся посреди
ячейки, получает первый прогноз на её границе, и число таких отказов видно в
счётчике `NoStateAtT`, а не выглядит как «машина спит». Подробно — ADR 0007.

Кадры уходят в ограниченную очередь `internal/scheduler`, из неё модель, а
ответы — в гейтвей. Очередь между конвейером и сетью обязательна: конвейер не
имеет права зависнуть из-за недоступного ML, потому что NDTP-пакеты приходят
независимо от прогноза. Отброшенные кадры считаются, и по счётчику видно,
модель не справляется или кадров просто слишком много. Подробно — ADR 0008.

Кадры, дошедшие до воркера в одной ячейке, обслуживаются одним запросом:
воркер берёт первый кадр и неблокирующим добором забирает всё, что уже лежит
в очереди, до `--batch` (по умолчанию 32). Ждать накопления не нужно: всплеск
на границе ячейки уже готовая пачка, а одиночный кадр в паузе уйдёт сразу и
не застрянет. Один кадр идёт обычным `POST /predict`, несколько —
`POST /predict/batch`; ответы сопоставляются по `sample_id`, и неизвестный или
пропущенный ответ считается ошибкой контракта, а не поводом догадываться по
индексу. Если модель ответила ошибкой, пачка разворачивается в поштучный
обход, чтобы кадры не потерялись. Отсутствие `/predict/batch` у модели
проверяется один раз. Подробно — ADR 0009.

Глубина очереди, число принятых, обслуженных, отброшенных и оставшихся при
остановке кадров, а также квантили времени обращения к модели публикуются в
`/metrics`. Вместе они отвечают на вопрос «мы медленные или модель», который по
одному числу неразличим: очередь могла копиться из-за модели, а могла из-за
нашей обработки. Гейтвей спрашивает планировщик и цепочку прогноза функциями
из `Config`, а не их типами, — иначе зависимость `gateway → scheduler` потянулась
бы в обе стороны, и собирать их пришлось бы в каждом новом месте.

### 4.1.1. Проверка потока на раздаче

Команда `transportctl replay` переигрывает размеченные данные тем же кодом и
сверяет результат с эталоном:

```bash
transportctl replay --plan test/schedule.csv --traffic test/traffic.csv \
    --labels labels/labels_test.csv
```

| проверка | результат |
|---|---|
| `labels_test.csv`, 353 метки | цель совпала **326 из 326** (100 %) |
| `validate/points.csv`, 151 метка | цель совпала **142 из 142** (100 %) |
| отклонено как «цель позади» | 27 и 8 соответственно |
| ключ кадра против `sample_submission.csv` | совпадает **142 из 142** |

Ноль расхождений по цели означает, что правило ADR 0005 не «похоже на
правильное», а совпадает с тем, по которому organizers строили точки прогноза.
Единственное намеренное расхождение — `cur_dev_s`, и оно измерено и описано в
[ADR 0004](adr/0004-cur-dev-leak-and-skew.md).

### 4.2. Порты

| Сервис | Порт | Назначение |
|---|---|---|
| `ndtp-ingest` (Go) | **9201/TCP** | NDTP-сервер для эмулятора |
| `gateway` (Go) | **8080** | REST + WebSocket + `/metrics` + Swagger UI |
| `ml-core` (Python) | **8000** | `/predict`, `/predict/batch`, `/model/info`, OpenAPI |
| `dashboard` (nginx) | **3000** | UI диспетчера |
| `ndtp-emu` (эмулятор) | 18080 | REST-конфиг эмуляции |

Порты 9201 и 8080 — один и тот же процесс `transportctl serve`: отдельный
`gateway` в расчёте не нужен, а состояние накопителя терять при перезапуске
нельзя.

### 4.3. Планировщик горизонта (критерий 2)

Каждые 30 с для каждого ТС сканируется план вперёд: выбираются остановки с
`time_begin ∈ (T + 10 мин; T + 15 мин]`, для каждой формируется прогнозная точка.
Логика **воспроизводит генерацию `validate/points.csv`** (сетка `T` = 300 с),
поэтому офлайн-CSV и живой эмулятор дают одинаковый формат точек.
`TICK=30s` для демо, `TICK=5m` для прода.

Инвариант: инцидент не создаётся, если `target_time_begin − T ∉ (600; 900]` секунд.
Отдельный тест проверяет, что ни один алерт не формируется «задним числом».

При неоднозначности (две строки расписания делят минимальное время в окне)
кадр **не выбирает одну из них молча**: он несёт оба варианта, а ключ
`sample_id` остаётся общим для пары. Ключ имеет вид `<tr_id>_<unix(T)>` — ровно
тот, что и в `labels/*.csv` и `sample_submission.csv`, поэтому кадр соединяется
с эталоном и с сабмитом без переименования.

### 4.6. Map matching (доп. фича)

1. Из планового расписания для каждого `(tr_id, order_date)` строим упорядоченную
   последовательность остановок и **полилинии маршрута** (геом в данных — только `POINT`,
   линий нет).
2. Маршруты кластеризуются по множествам геом (Jaccard / greedily) → у каждого ТС свой `route_id`.
3. День делится на рейсы: смена направления детектируется по повтору геома в пределах ~15 мин.
4. Привязка точки к маршруту: ближайшая вершина + фильтр по курсу (heading error) + фильтр
   по расстоянию (≤ 80 м) + сглаживание по времени. При промахе — точка помечается как off-route
   и идёт в признак `location_valid_ratio`, а не выбрасывается.
5. Из привязки считается `distance_to_target` вдоль маршрута и `stops_remaining`.

### 4.7. Деградация (критерий 5)

| Отказ | Поведение |
|---|---|
| Эмулятор/поток NDTP молчит | `staleness` растёт, на карте ТС помечается серым «нет данных», используется last-known-state |
| NDTP обрыв → reconnect | handshake FSM с экспоненциальным backoff, автовосстановление |
| ML-сервис недоступен | circuit breaker → отдаём последние прогнозы, помечаем устаревание и возвращаем их исходный `as_of` |
| Модель не справляется с темпом | переполнение очереди прогнозов: кадры отбрасываются и считаются, приём телеметрии продолжается |
| Эмулятор недоступен целиком | авто-старт replay исторического CSV на тех же интерфейсах |
| Модель не загрузилась | fallback на правило `pred = cur_dev_s` с явной пометкой |
| Плана по ТС нет | ТС отслеживается, но без прогноза; на карте — иным стилем |

Каждая деградация видна в UI и в `/metrics` — это демонстрируется жюри отдельным сценарием.

## 5. Модель

**Цель:** MAE ≤ 55 с (4 балла) с реальным шансом на ≤ 45 с (5 баллов).
6 баллов (≤ 32.4 с) при std таргета 130 с — крайне тяжёлая цель, строить план ради неё нельзя.

### 5.1. Дорожная карта

| Этап | Модель | Ожидаемый MAE | Баллы |
|---|---|---|---|
| v0 | `pred = cur_dev_s` (baseline) | 88.7 | — |
| v1 | CatBoost MAE-objective, табличные признаки | ~70 | 2–3 |
| v2 | + признаки движения (простой, скорость, дистанция, участок) | ~58–62 | 3–4 |
| v3 | **таргет = дельта** `target − cur_dev`, предсказание прибавляется к `cur_dev` | ~52–57 | 4 |
| v4 | + CatBoost-классификатор `P(late)`, блендинг `E[delay]` и порога риска | ~50–55 | 4–5 |
| v5 | ансамбль с PyTorch temporal encoder → ONNX | −2…−4 с от v4 | 4–5 |

Предсказание дельты вместо абсолютного значения — ключевой приём: он снимает почти весь
масштаб `cur_dev` и оставляет модели учить только накопление отклонения.

### 5.2. Признаки (все строго as-of на момент `T`)

- **Дано из `points.csv`:** `cur_dev_s`, `target_time_begin`, горизонт, `target_stop_id`.
- **Дрейф-история:** отклонения на последних k остановках, их разности, тренд
  (линейная регрессия по 5 точкам), число подряд идущих поздних, знак последних 3 разностей.
- **Простой:** `dwell_current`, `dwell_last`, `dwell_p90_route`, `dwell_rolling_3/5`,
  доля точек `speed == 0` за 1/3/5/10 мин.
- **Скорость:** средняя/макс/текущая на 1/3/5/10 мин, доля `speed < 3`,
  **дефицит скорости vs профиль участка в это время суток**.
- **Геометрия:** `distance_to_target` вдоль маршрута, `stops_remaining`, `heading_error`,
  позиция на маршруте (0..1), `location_valid_ratio`, `off_route_ratio`.
- **План:** плановое время в пути до цели, `slack = plan_travel − typical_travel`,
  интервал движения по маршруту, номер рейса.
- **Контекст:** час, флаг пика, день недели, `manual_fill`, `n_vehicles_on_route`,
  headway до предыдущего ТС на маршруте.
- **Качество данных:** `staleness`, число точек в окне, лаг `receive_time − event_time`.

### 5.3. Защита от утечки в обучении

- Только `event_time ≤ T`; все соединения — as-of (`polars` lazy + `search_sorted`).
- Тест-инвариант: перемешать все строки строго после `T` иAssert, что хеш вектора признаков
  не изменился. Этот тест обязателен в CI.
- `time_fact_begin` **никогда** не попадает в признаки — только в таргет, и только
  на момент `T + 10…15 мин`, как определено генератором точек.
- Модель обучается на `train/` и валидируется на `labels_test.csv`; `oracle_audit.py`
  используется исключительно как финальная честная метрика, не как источник обучения.

### 5.4. Причина сбоя (для карточки инцидента)

4 класса, правила + мини-классификатор CatBoost:

| Код | Триггер |
|---|---|
| `dwell_long` | простой > p90 по маршруту (длительная посадка) |
| `congestion` | дефицит скорости на сегменте vs профиль |
| `incident` | резкая остановка вне остановки, `location_valid` теряется |
| `schedule_slack` | ТС опережает, но плановое время в пути не покрывает накопленный простой |

### 5.5. What-if (доп. фича)

Вставка виртуального ТС на выбранную остановку с заданным headway → прогон простой
queueing-модели по цепочке остановок маршрута → дельта прогнозируемой задержки
и «время восстановления графика». Модель наивная, её приблизительность явно подписана в UI.

### 8.1. Разбор NDTP

Протокол разбирается пакетом `backend/internal/ndtp` без кодогенерации:
`proto/ndtp.proto` не создаётся. Причина и рассмотренные альтернативы —
в [ADR 0001](adr/0001-ndtp-parser-in-go.md).

Кадр: NPL 15 байт, NPH 10 байт, little-endian, сигнатура 0x7E7E, CRC-16/Modbus
(poly 0xA001, init 0xFFFF) над NPH вместе с телом, в NPL — со свапом байтов.
Handshake — NPH type 100, тело 18 байт; телематика — type 101, serviceId 1.
Типа ячейки 1 в протоколе нет.

В каждом кадре ровно один NPH: `dataSize = 10 + длина тела`. Флаговые слова
NPL и NPH устроены по-разному, и это важно:

| Слово | бит 0 | бит 1 | бит 2 | биты 3… |
|---|---|---|---|---|
| флаги NPL | `nplFlagEncryption` | `nplFlagCrc` | `nplFlagDelay` | `flags`, 13 бит |
| флаги NPH | `nphFlagRequest` | `flags`, 15 бит | | |
| флаги тела handshake | `connectionEncryptionFlag` | `connectionCrcFlag` | `connectionSimulateFlag` | `connectionFlags`, 13 бит |

Бит запроса существует только в NPH. Эмулятор вендора всегда заполняет поле
CRC и никогда не выставляет `nplFlagCrc`, поэтому сумма проверяется
независимо от флага, а кадры `NPL_TYPE_ERROR` (1) и `NPL_TYPE_DEBUG` (3) не
принимаются.

Идентификаторы типов пакетов переиспользованы между сервисами, поэтому сам по
себе тип не определяет назначение — нужно знать и `serviceId`:

| serviceId | сервис | тип 0 | тип 100 | тип 101 |
|---|---|---|---|---|
| 0 | GenericControls | `RESULT` | `CONN_REQUEST` | — |
| 1 | Navdata | `RESULT` | `HISTORY` | `REALTIME` |

Телеметрию несёт только `REALTIME` сервиса Navdata. `RESULT` и `HISTORY`
известны протоколу, но не несут телеметрии: они учитываются метрикой
`SkippedPackets` и не разрывают соединение. Любой другой тип или сервис
разрывает соединение как структурная ошибка.

Шифрование не реализовано. Кадр, объявивший шифрование в NPL или в теле
handshake, отклоняется явно со счётчиком `EncryptedRejects`, чтобы
шифротекст не разбирался как данные. Границы того, что подтверждено
байткодом вендора, а что нет, перечислены в комментарии
`TestValidationBoundariesAreDocumented`.

Длина ячейки в потоке не передаётся, поэтому границы определяются по типу
через таблицу размеров. Все 23 типа зарегистрированы и полностью декодируются:

| Тип | Имя | Байт | Тип | Имя | Байт |
|---|---|---|---|---|---|
| 0 | Nav00 | 26 | 14 | Bms14 | 15 |
| 2 | IntSensor02 | 26 | 15 | Lls15 | 50 |
| 3 | Crown03 | 14 | 16 | Termo16 | 8 |
| 4 | Irma04 | 15 | 17 | Alcohol1st17 | 46 |
| 5 | Kdm05 | 6 | 18 | CAN18 | 50 |
| 6 | Idn06 | 9 | 19 | GSMstations19 | 40 |
| 7 | Idn07 | 1 | 20 | M333CAN20 | 8 |
| 8 | Usi08 | 6 | 21 | Alcohol2nd21 | 180 |
| 9 | Reg09 | 40 | 22 | ServerStatistics22 | 24 |
| 10 | Can10 | 37 | 23 | TrackerStatistics23 | 16 |
| 12 | Rfid12 | 5 | 100 | ZipSensorData100 | 44 |
| 13 | Plo13 | 13 | | | |

Порядок полей и их разрядность восстановлены из байткода классов вендора
(`BOOT-INF/classes/.../navdata/cells/G6Cell*.class`), а не взяты из
документации. Раскладка проверена тремя независимыми способами:

1. Сумма ширин полей каждого типа совпала с измеренным на эмуляторе размером
   payload — 23 из 23.
2. Эмулятору через конфигурацию заданы различимые значения **каждого** поля
   **каждого** типа; пакет с ответом разобран и сверен поле в поле
   (`TestWireFormatFieldsMatchVendorSerializer`). Это подтверждает и порядок
   полей, и разрядность, и то, что битовые поля (`Bms14`, `Irma04`)
   упаковываются с первого младшего бита.
3. Автосгенерированный пакет со всеми 23 типами целиком разбирается без
   остатка: 725 байт тела, ровно 23 ячейки.

В режиме `autoGenerate` эмулятор шлёт 5 ячеек: Nav00, Usi08, Termo16,
IntSensor02, Can10 — без Lls15. Эмулятор всегда добавляет Nav00 к запрошенным
ячейкам, даже при `autoGenerate: false`. Ячейки, перечисленные в конфигурации,
заполняются заданными значениями; без явных значений приходят нулями. На живых
пакетах подтверждено, что `Nav00.SpeedAvg` совпадает с `Can10.Speed`.

Разбор строгий: неизвестный тип ячейки, нехватка байт, несовпадение CRC,
неверная сигнатура, неожиданный `serviceId` или тип NPH и лишние байты в конце
тела рвут соединение, причина фиксируется в метриках. Штатное отключение
устройства (`EOF`) ошибкой не считается. Пакеты эмулятора сохранены в
`backend/internal/ndtp/testdata/golden` и служат основой тестов, поэтому тесты
не требуют Java и Docker.

CRC-16/Modbus реализован внутри пакета: `hash/crc16` отсутствует в
используемой сборке Go. Эталонный вектор `123456789` даёт 0x4B37.

| 1 | MAE ≤ 32.4 с практически недостижим | планируем от 4–5 баллов; 6-й балл не является основанием архитектуры |
| 2 | В системе Python 3.14, под него нет wheels torch/catboost | `uv python install 3.12`, пин версии в `pyproject.toml` и в образе |
| 3 | На демо у жюри может не быть интернета | вендоренный стиль MapLibre + фолбэк на canvas, полилинии строим сами |
| 4 | Рост объёма признаков на Go | жёсткий контракт `features/v1.yaml` + golden-тест replay ↔ live |
| 5 | Соблазн зашить оракул в prediction-path | оракул изолирован в `scripts/oracle_audit.py`, описан открыто в README |
| 6 | Ошибки в разборе little-endian / CRC | golden-файлы с реального эмулятора + тест на каждый тип ячейки |
| 7 | Смещение train→validate (train частично синтетический) | приоритет валидации на реальных `test`/`validate`, вес реальных примеров |

## 10. План работ

| Фаза | Содержание | Результат |
|---|---|---|
| **0** | `uv`-env, `oracle_audit.py`, `docs/data-audit.md` | точный локальный MAE + отчёт об утечке |
| **1** | Go: NDTP-декодер + golden-тесты на пакетах эмулятора | закрыт риск протокола | **выполнен** |
| **2** | Go: `statestore` + `stopdetect` + `mapmatch` + офлайн-выгрузка признаков | parquet с признаками, детекция прибытий |
| **3** | Python: v1 → v3 CatBoost, отбор по оракулу | MAE ≤ 60 |
| **4** | Go: gateway, OpenAPI, WebSocket, планировщик горизонта | end-to-end поток |
| **5** | Дашборд: карта, риск, карточки, live-обновления | критерий 4 |
| **6** | Docker, метрики, деградация, Sphinx / GoDoc / OpenAPI | критерии 3 и 5 |

## 11. Итого

1. **Писать NDTP-парсер на Go** — бинарный протокол без библиотек, модель «одно соединение
   на терминал», требования к p99 и к холодному старту. Python в ML-модуле нужен и так,
   но к проводу он не прикасается.
2. **Весь онлайн-контур на Go**, три признака из критерия 3 считаются именно в Go,
   тяжёлая статистика по окну — в Python, но **одной и той же функцией** для обучения и сервиса.
3. **Реалистичный фокус** — 4–5 баллов по критерию 1 при полном закрытии критериев 2–5
   и получении дополнительных фич. Это суммарно 22–23 балла из 26 основного этапа.
4. **Утечка в данных** используется только как локальный оракул для честного измерения
   и раскрывается жюри прозрачно.
