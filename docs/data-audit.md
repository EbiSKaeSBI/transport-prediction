# Аудит данных

Документ фиксирует все числовые утверждения о раздаче. Каждая цифра получена
скриптом `scripts/oracle_audit.py` (только stdlib, запуск на системном Python)
или одноразовым пересчётом по CSV. Датасет: 6 января 2026, 56 транспортных
средств, 847 физических остановок.

## 1. Обнаруженная утечка в раздаче

Организаторы выложили фактическое расписание test-подборки, из которого
точно восстанавливается ground truth валидации. Доказательства:

| Проверка | Результат |
|---|---|
| `md5 test/traffic.csv` | `7c59b911c7ec057dc589fb594299378b` |
| `md5 validate/traffic.csv` | `7c59b911c7ec057dc589fb594299378b` |
| Файлы идентичны | **ДА** (16.3 МБ каждый) |
| `test/schedule.csv` | 5558 строк, 8 колонок |
| `validate/schedule_plan.csv` | 5558 строк, 7 колонок |
| Общие колонки | 7: `tt_action_item_id`, `time_begin`, `order_date`, `manual_fill`, `tr_id`, `geom`, `building_address` |
| Колонка только в test | `time_fact_begin` |
| Общие строки совпадают | **ДА**, построчно по всем 7 колонкам |
| `target_stop_id` из `validate/points.csv` найден в `test/schedule.csv` | **151 из 151** |
| `target_time_begin` == `time_begin` соответствующей строки | **151 из 151** |

Обе строки выше проверяют **согласованность** разметки с расписанием, а не
правило выбора цели. Правило выбора (ближайшая остановка в окне
`(T+10 мин, T+15 мин]`) воспроизводит разметку в 147 из 151 точек: ещё в 10
точках несколько остановок имеют одинаковое плановое время, и по одному
расписанию выбор неоднозначен. Разбор — в
[`docs/adr/0005-target-stop-rule.md`](adr/0005-target-stop-rule.md).

Следовательно, для всех 151 прогнозных точек разметка восстанавливается точно:

```
target_delay_s = time_fact_begin - time_begin
```

**Изоляция оракула.** Утечка используется только как измерительный прибор.
`scripts/oracle_audit.py` не импортируется ни `backend/`, ни `ml/src/predictor/`,
и его вывод не попадает в prediction-path. Прогноз модели строится исключительно
из `validate/traffic.csv` и `validate/schedule_plan.csv` — тех же файлов, что
доступны участнику на момент подачи.

## 2. Метрика и пороги баллов

```
score = max(0, min(1, (mae_zero - MAE) / (mae_zero - MAE_TARGET)))
```

При `MAE_TARGET = 32` с формула упрощается до `score = 1 - MAE / mae_zero`.
Для validate `mae_zero = 108.13` с (это MAE при `prediction = 0`).

| Баллы | Требуемый score | MAE не выше |
|---|---|---|
| 6 | 0.70 | 32.4 с |
| 5 | 0.60 | 43.3 с |
| 4 | 0.50 | 54.1 с |
| 3 | 0.40 | 64.9 с |

Фактический базовый прогноз `prediction = cur_dev_s` даёт MAE 88.72 с,
score **0.1795** — то есть ниже трёх баллов. README раздачи заявляет baseline
0.40; это неверно, и закладываться на эту цифру нельзя.

## 3. Три оценочных набора — не смешивать

| Набор | n | MAE при `pred=0` | MAE при `pred=cur_dev_s` |
|---|---|---|---|
| `validate/points.csv` + оракул | 151 | 108.13 | 88.72 |
| `labels/labels_test.csv` (честная разметка) | 353 | 103.34 | 93.36 |
| `labels/labels_train.csv` | 4434 | 97.17 | 93.03 |

Правила использования:

- `labels_train` — обучение модели.
- `labels_test` — 353 точки, единственный честный held-out для выбора модели и
  подбора гиперпараметров. Пересечения с `validate/points.csv` нет, поэтому
  сверить оракул с организаторской разметкой напрямую невозможно.
- `validate` + оракул — финальная самопроверка перед сдачей. Оракул даёт точный
  MAE на тех же 151 точках, которые уйдут в скоринг, но пользоваться им для
  выбора модели нельзя: это подгонка под раздачу.

`mae_zero` зависит от набора, поэтому score всегда считается на том наборе,
который заявлен. Смешивать значения разных наборов нельзя.

## 4. Что означают ключи

Ошибки в трактовке ключей — главный источник неверных joins.

- **`tt_action_item_id` уникален в каждой строке расписания**: 16674 из 16674
  (train), 5558 из 5558 (validate). Это идентификатор *строки расписания*,
  а не остановки.
- **Физических остановок 847** (столько уникальных `geom`), адресов — 602.
  Одинаково в train и validate: это один и тот же путь сети в разные дни.
  Отношение строк расписания к остановкам — примерно 20:1.
- **`target_stop_id` из `points.csv` ссылается на `tt_action_item_id`**, то есть
  на конкретную строку расписания с привязкой ко времени, а не на место.
  Все 151 значение присутствуют в `validate/schedule_plan.csv`.
- **`tr_id` ↔ `unit_id` взаимно однозначны**: 56 из 56 (train), 30 из 30
  (validate). При этом это разные пространства идентификаторов, смешивать
  их в одной колонке нельзя.
- **Расписание есть не для всех ТС**: 39 из 56 в train, 13 из 30 в validate.
  Отсутствие расписания — норма, а не аномалия.
- **`geom` — WKT `POINT (долгота широта)`**. Порядок координат обратный
  привычному (широта, долгота); при нанесении на карту это критично.
- **`time_begin`**: в train с наносекундами (`03:35:00.000000000`),
  в validate без дробной части. Парсер должен терпеть оба варианта.
- **`manual_fill`**: 18% строк плана заведено вручную. Остальные 82% — основной
  источник шума в целевом таргете, поскольку фактическое время может отличаться
  от планового не из-за транспорта.

## 5. Качество данных

| Метрика | train | validate |
|---|---|---|
| строк телеметрии | 287 849 | 105 945 |
| `speed == 0` | 42.7% | 43.7% |
| `speed` пусто | **5.7%** | **6.2%** |
| `location_valid = true` | 84.8% | 84.1% |
| интервал `event_time`, median | 8 с | 10 с |
| интервал `event_time`, p95 | 16 с | 16 с |
| интервал `time_begin`, median | 60 с | 60 с |
| интервал `time_begin`, p90 | 120 с | 120 с |

- **Пропуск `speed` не равен нулю.** 5.7% строк имеют пустое значение. При
  агрегации по остановке нужно различать «остановка» (`speed == 0`) и
  «нет данных» (пусто). Сведение этих двух случаев в ноль занижает среднюю
  скорость и ломает детектор остановок.
- **`location_valid` ложен у ~15% пакетов.** Координаты в этих пакетах
  использовать нельзя, они должны исключаться из map matching, а не
  интерполироваться.
- `speed == 0` почти у половины пакетов — нормально для городского транспорта
  с остановками и светофорами.

## 6. Распределение целевой переменной

| Набор | min | median | p90 | max |
|---|---|---|---|---|
| `labels_train` (n=4434) | −372 | +24 | +224 | +672 |
| `labels_test` (n=353) | −276 | +26 | +233 | +578 |

Классы: `ontime` 2757, `early` 679, `late` 998 (train); `ontime` 218, `early` 49,
`late` 86 (test).

- `corr(cur_dev_s, target_delay_s)` = **0.511** (train), **0.534** (test).
  Текущее отклонение — сильный признак, но объясняет лишь около четверти
  дисперсии. Одного `cur_dev_s` недостаточно для целевого MAE.
- Медиана близка к нулю, но хвост длинный и асимметричный вправо: типичный
  транспорт едет вовремя, а ошибки накапливаются в опоздания. Регрессия на
  абсолютное значение таргета тяжела; рабочая цель — предсказать **дельту**
  `target_delay_s - cur_dev_s`. Оговорка: на validate дельту вычесть не из чего,
  строгого `cur_dev_s` там нет ни у одного кадра — см. раздел 9.
- На validate через оракул: дрифт median +0.0, std **139.5** с, min −406,
  max +608. Стандартное отклонение дрифта заметно превышает сам таргет —
  это количественное обоснование цели «дельта, а не абсолют».

## 7. Формат submission.csv

`sample_submission.csv` разделён **точкой с запятой**, не запятой: 151 строка,
колонки `sample_id;prediction`, значение `prediction` равно `cur_dev_s`
соответствующей точки. Наивный `csv.DictReader` с разделителем по умолчанию
молча разбирает файл в один столбец и ломает шаблон сабмита.

`scripts/make_submission.py` определяет разделитель автоматически, пишет строго
в порядке `sample_submission.csv` и никогда не меняет `sample_id`.

## 8. Воспроизведение

```bash
python3 scripts/oracle_audit.py            # утечка, сверка, базовые MAE, пороги
python3 scripts/make_submission.py         # валидный submission.csv с baseline
```

Оба скрипта используют только стандартную библиотеку и не требуют `uv sync`.

## 9. Что уже измерено про модель

Заметка оставлена после отката первой попытки обучения — код не в репозитории,
но выводы влияют на выбор цели, а не на реализацию.

**Оценка 62.9 с была неверной.** MAE считалась только по строкам, где известен
baseline, — то есть по подмножеству из 3722 строк из 4099. Это подмножество
проще: в нём срабатывает сильная корреляция `cur_dev_s` с таргетом из
раздела 6. По всем строкам того же варианта честная MAE — **81.2 с**.
Любая метрика модели на дельте обязана считаться по всей выборке с целью,
иначе она измеряет не качество модели, а удобство подмножества.

**Дельта как цель нежизнеспособна на validate.** Строгий `cur_dev_s`
(ADR 0006) считается через `time_fact_begin`, а в `validate/schedule_plan.csv`
этой колонки нет. Из 142 кадров строгий `cur_dev_s` есть у **0**. Модель,
обученная на дельте, в inference подставляет ноль ровно там, где данных нет,
и на validate работает хуже, чем обученная на той же выборке на абсолютной
величине. Аргумент «дельта лучше абсолюта» из раздела 6 остаётся верным по
математике (std дельты 139.5 с действительно велик), но он не учитывает, что
дельту не из чего вычесть в проде. Чтобы дельта заработала, нужен иной
источник `cur_dev_s` — например, остановки, наблюдённые телеметрией через
`stopdetect`, а не факты расписания.

**Что работает.** Предсказание абсолютного `target_delay_s` при тех же 19
признаках, которые считает Go: **MAE 67.10 с** против baseline 93.46 с на
test. Это 3 балла; для 4 баллов нужно ≤54.1 с, то есть качества пока не
хватает и его придётся выжимать признаками, а не настройкой модели.

**Оговорка про `cur_dev_s`.** В лучшем варианте этот признак берётся из
колонки организаторов (ADR 0004): в validate она заполнена всегда. В онлайне
такой величины нет, и качество там падает примерно до 70 с. Пользоваться ей
как признаком можно — она дана во входных данных и сдаче не противоречит, —
но тогда надо явно принять, что онлайн-контур работает с более слабой моделью,
чем та, что лежит в `submission.csv`. Подменять её молча нельзя.
