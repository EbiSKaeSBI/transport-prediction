# Как работает проект

От бинарного пакета NDTP до красной точки на карте диспетчера и до `submission.csv`.
Пример проведён на настоящей прогнозной точке `131672_1767670500`; все числа — реальные.

---

## 1. Два контура

| Контур | Когда | Что делает | За что отвечает |
|---|---|---|---|
| **OFFLINE** | до подачи, на CSV | обучает модель, строит `submission.csv` | критерий 1 (0–6) |
| **ONLINE** | на демо, на потоке NDTP | принимает поток, предсказывает, рисует дашборд | критерии 2–5 (0–20) |

Связка между ними задумана как **один и тот же код признаков**
(`backend/internal/features` в Go): онлайн вызывает его на живом потоке,
офлайн — на исторических CSV. Это единственный способ исключить расхождение
между обучением и эксплуатацией конструктивно, а не аккуратностью разработчика.

> **Статус: реализованы `backend/internal/features`, `horizon` и команда
> `transportctl replay` (выход — JSONL-кадры, не parquet), а также ML-пакет
> `ml/src/predictor` (dataset/train/predict, ватерлайн v1b — MAE оракула
> 58.2 с на validate).** Контур приёма NDTP (`serve`, `ndtp-capture`,
> `ndtp-inspect`) работает. Не реализованы пока: gRPC-сервис предсказаний
> (#26) и дашборд-рассылка.
> Схема ниже — целевая архитектура.

```
                      FEATURE CONTRACT v1  (features/v1.yaml)
                      имена · типы · порядок · единицы · null
                                  │
             ┌────────────────────┴────────────────────┐
             ▼                                         ▼
   Go: statestore + stopdetect              Go: transportctl replay
       + mapmatch + features                       │
             │  FeatureFrame                        │ features.parquet
             ▼                                      ▼
   Python: predictor.inference              Python: predictor.train
             │                                      │
             ▼                                      ▼
      дашборд, алерты                      CatBoost → model.json
                                                    │
                                                    ▼
                                            submission.csv
```

## 2. ONLINE: путь одного пакета до пикселя

### 2.0. Исходные данные

```
sample_id           131672_1767670500
tr_id               131672
T                   03:35:00          ← момент построения прогноза
целевая остановка   Салтыковская ул., д.1А
плановое прибытие   03:50:00
горизонт            15 минут
cur_dev_s           274               ← ТС опаздывает на 4 мин 34 с
```

Снимок телеметрии, доступный строго в момент `T`:

| Окно | Точек | Ср. скорость | Простой | `location_valid` |
|---|---|---|---|---|
| 5 мин | 32 | 16.0 км/ч | 14 % | 88 % |
| 10 мин | 61 | 18.1 км/ч | 13 % | 89 % |
| 15 мин | 92 | 18.7 км/ч | 13 % | 89 % |

```
03:33:47  speed=12.0  heading=234  valid=True
03:33:50  speed=—     heading=—    valid=False   ← потеря геолокации
03:34:01  speed=22.0  heading=230  valid=True
03:34:31  speed=23.0  heading=230  valid=True
03:34:41  speed=0.0   heading=0    valid=True    ← стоит на остановке
03:34:41  speed=14.0  heading=240  valid=True    ← тронулся
03:34:45  speed=9.0   heading=240  valid=True
```

Свежесть последнего пакета — **15 секунд**. По всей validate свежесть ≤ 1 минуты
для **151 из 151** точки: поток доступен на всех прогнозных точках.

### 2.1. Пакет приходит на TCP

Эмулятор (или `transportctl replay`) открывает соединение на `9201`, шлёт
`NPH_SGC_CONN_REQUEST`, затем `NPH_SND_REALTIME`.

### 2.2. Go декодирует (~30 мкс)

```
┌ NPL 15 байт ┬ NPH 10 байт ┬ ячейка Nav00: 26 байт ┐
│ 0x7E7E      │ serviceId=1  │ timestamp             │
│ dataSize=36 │ type=101     │ longitude, latitude   │
│ CRC-16      │ requestId=N  │ extraDopBit0…7        │
│ type=2      │ flags        │ speedAvg, course      │
└─────────────┴──────────────┴───────────────────────┘
```

1. Читаем `dataSize` байт после NPL.
2. Считаем CRC-16/Modbus по NPH + телу, сверяем с NPL (байты переставлены).
   Расхождение → пакет отброшен, `ndtp_crc_errors_total++`, соединение не рвём.
3. Разбираем ячейки `[type:u8][number:u8][payload]`, `Nav00` идёт первой.
4. Распаковываем `extraDopBit5/6` (знаки координат) и `extraDopBit7` (валидность).
5. Получаем `VehicleFrame{t, tr_id, lon, lat, speed, heading, valid}`.

Дёшево: буфер на переиспользуемом массиве фиксированного размера, без аллокаций,
без JSON. На 3 msg/s это неизмеримо, но p99 предсказуем при росте до десятков тысяч
соединений — один goroutine + `bufio.Reader` на `unitId`.

### 2.3. Кольцевой буфер состояния ТС

Размер — **90 точек = 15 минут** при интервале 10 с.

Ключевое решение, вытекающее из смысла задачи: прогноз нужен за 10–15 минут, поэтому
пакет старше 15 минут **не имеет ценности**. Отсюда:

- память не растёт, ничего не вытекает;
- при обрыве связи у диспетчера остаётся last-known-state, а не дыра в данных;
- отсюда же отказ от брокера: буферизовать нечего.

### 2.4. Детекция простоя и прибытия

```
speed == 0  ∧  расстояние до плановой остановки < 80 м  ∧  повтор 2+ точек подряд
```

Из 92 точек за 15 минут **13 % имеют `speed == 0`**. Это главный сигнал: посадка и
высадка пассажиров съедает время и роняет график.

Защита от ложных срабатываний: остановка в пробке в середине маршрута не считается
прибытием — не выполнено условие близости к плановой остановке. Всплеск `speed == 0`
на светофоре отсекается требованием двух точек подряд и порогом длительности.

### 2.5. Сопоставление с расписанием

Go определяет **текущий рейс и направление**, затем находит плановое время остановки.

Почему это неочевидно: в данных **нет `route_id`**, а расписание на сутки — плоский
«туда-обратно ×2». Одна остановка встречается дважды за 10–15 минут:

```
план 03:34:00  факт 03:39:15  +315 с  Салтыковская ул., д.1А
план 03:50:00  факт 03:51:18   +78 с  Салтыковская ул., д.1А   ← тот же адрес
```

Смена направления детектируется по повтору геома в пределах ~15 минут, и прогноз
привязывается к конкретному рейсу, а не к «остановке вообще».

Результат — **`cur_dev_s`**, который в датасете дан как подсказка, а в онлайне мы
вычисляем его сами: `факт 03:39:15 − план 03:34:00 = +315 с`.

### 2.6. Срабатывает планировщик горизонта

Каждые 30 с для каждого ТС ищем остановки с

```
T + 10 мин  <  time_begin  ≤  T + 15 мин
03:45       <  03:50       ≤  03:50   ✓
```

Это **ровно та логика, которой организаторы сгенерировали `validate/points.csv`**
(сетка `T` = 300 с). Офлайн-файл и живой поток дают точки одинакового формата.

**Инвариант критерия 2:** инцидент не создаётся, если
`target_time_begin − T ∉ (600; 900]` секунд. Отдельный тест проверяет, что ни один
алерт не формируется «задним числом». Тик (`--tick`, по умолчанию 15 с) проверяет
наступление границы; считает моменты прогноза сетка в пять минут (`--grid`),
округляя `T` вниз. Тик 15 с при сетке в 5 минут даёт 20 проверок на одну ячейку,
и кадр строится на первой.

### 2.7. Сбор признаков

**Считает Go** (перечислено в критерии 3):

```
cur_dev_s               = 274
speed_avg_segment_300s  = 16.0 км/ч     ← «средняя скорость на сегменте»
dwell_current           = 0 с           ← «время простоя»
dwell_last, dwell_rolling_5
distance_to_target, stops_remaining, heading_error
location_valid_ratio    = 0.89
```

**Считает Python** поверх окна (одна функция `features()` для train и serve):

```
speed_ma_5m / 10m / 15m = 16.0 / 18.1 / 18.7
speed_deficit_vs_profile
neighbor_speed_on_segment
тренд отклонения, импульс
```

### 2.8. Запрос в ML Core

```
Go → Python  POST /predict  (HTTP + JSON)
  { sample_id, unit_id, tr_id, t, target_stop_id, horizon_s,
    target_ambiguous, features {21 признак} }

Python → Go
  { delta_s: 96, p_late: 0.31, model_version: "v3" }
```

Имена 21 признака едут вместе с кадром, и модель сверяет их со своим
контрактом: расхождение обязано падать, а не предупреждать.

Таймаут, ретраи с backoff, circuit breaker. При недоступности ML — последний
известный прогноз модели с флагом устаревания и его исходным `as_of`, затем
baseline: `delta_s = 0`, то есть `pred = cur_dev_s`.

Между конвейером и моделью стоит ограниченная очередь: недоступность ML не
должна останавливать приём телеметрии. Отброшенные кадры считаются и видны в
сводке и в `/metrics`.

Кадры, дошедшие до воркера на одной границе сетки, уходят одним запросом:
`POST /predict/batch` с массивом `frames` вместо последовательности одиночных
запросов. Ответы приходят вразнобой и сопоставляются по `sample_id`; если
модель ответила ошибкой, пачка разворачивается в поштучный обход, чтобы
кадры не пропали. Утверждения об этом — в ADR 0009.

### 2.9. Решение об инциденте

`predicted 96 c < порог 120 c` → инцидент не создаётся, ТС зелёная.

| Условие | Цвет |
|---|---|
| `delay_s < 60` и `p_late < 0.3` | зелёный |
| `60 ≤ delay_s < 120` или `0.3 ≤ p_late < 0.6` | жёлтый |
| `delay_s ≥ 120` или `p_late ≥ 0.6` | красный, создаётся карточка |

### 2.10. Дашборд

Go пишет прогноз в Postgres и рассылает событие по WebSocket:

```json
{"type":"vehicle_update","tr_id":131672,"delay_s":96,
 "p_late":0.31,"risk":"yellow","dwell_s":0}
{"type":"incident","sample_id":"131672_1767670500","delay_s":96,
 "reason":"schedule_slack","segment":"Салтыковская ул. д.1А"}
{"type":"metrics","p95_ms":34,"queue_depth":0,"active_vehicles":30}
```

Позиции шлются клиенту **не чаще 1 раза в секунду** независимо от частоты пакетов.
От пакета NDTP до пикселя на экране — **менее секунды**.

## 3. Что модель должна уметь: разбор примера

Полный план-факт по ТС 131672 вокруг `T`:

```
план 03:26:00 | факт 03:31:22 | +322 с | Суздальская ул., д.15А
план 03:28:00 | факт 03:33:35 | +335 с | Новокосинская ул., д.27
план 03:31:00 | факт 03:35:54 | +294 с | Новокосинская ул., д.13, к.2
план 03:34:00 | факт 03:39:15 | +315 с | Салтыковская ул., д.1А   ← конечная
       …        16 минут перерыва / разворота …
план 03:50:00 | факт 03:51:18 |  +78 с | Салтыковская ул., д.1А   ← ЦЕЛЬ
план 03:51:00 | факт 03:52:18 |  +78 с | ул. Николая Старостина
план 03:58:00 | факт 04:01:18 | +198 с | Суздальская ул., д.15А
```

**Автобус опоздал на 315 с, затем 16 минут стоял на развороте и наверстал 237 с.**

| | Значение |
|---|---|
| `cur_dev_s` (baseline) | 274 с |
| Истинная задержка | **+78 с** |
| Ошибка baseline | **196 с** |

**Вывод для архитектуры:** модель обязана детектировать **перерыв / разворот** —
участок, где между плановым прибытием и следующим отправлением есть 10+ минут slack.
Внутри такого окна задержка **сжимается сама**, и предсказывать `cur_dev` нельзя.

| Новый признак | Зачем |
|---|---|
| `layover_min` — минуты между предыдущим прибытием и отправлением | главный сигнал восстановления |
| `is_terminal_stop` | на конечной задержка всегда «схлопывается» |
| `slack_to_target` | сколько встроенного времени до цели |
| причина `schedule_slack` | прямо в карточку инцидента |

Без этих признаков мы **систематически переоцениваем** задержку на конечных остановках,
а MAE считает эту ошибку дважды — на всех точках класса.

## 4. OFFLINE: как делается сабмит

> **Статус: шаги 1–5 конвейера реализованы** (2026-09-25, ветка
> `feature/phase3-ml`): офлайн-признаки считает тот же Go-код, что онлайн
> (`transportctl replay`), модель и инференс — `ml/src/predictor`.
> Отличия от целевой схемы: шаг 1/3 — выход JSONL вместо parquet
> (`predictor.dataset` конвертирует его в датасет-паркиеты с python-секциями
> window/context), шаг 2 — таргет пока абсолютный `target_delay_s`
> (дельта `target − cur_dev` — задача #25), шаг 5 — режим `--model` работает,
> финальная перегенерация корневого `submission.csv` — задача #27.
> Последовательность:

```
1. transportctl replay -plan train/schedule.csv -traffic train/traffic.csv
     -labels labels/labels_train.csv -out ml/artifacts/features_train.jsonl
   + python -m predictor.dataset → dataset_train.parquet
     (те же Go-признаки, что в онлайне + python-секции as-of T)

2. python -m predictor.train
   polars → CatBoostRegressor(loss="MAE")
   таргет = target_delay_s (v1/v2) → target_delay_s − cur_dev_s (#25)
   метрика: MAE на dataset_test (holdout) + oracle_audit --predictions
   → model_v1b.json + metrics_v1b.json (список фич и важности в нём)

3. transportctl replay -labels validate/points.csv -out ... + predictor.dataset
   → dataset_validate.parquet (142 кадра; cur_dev_s — хинт, ADR-0004)

4. python -m predictor.predict --dataset dataset_validate.parquet
   → predictions_validate.csv (sample_id;prediction)

5. python scripts/make_submission.py --model predictions_validate.csv
   → submission.csv   (sample_id;prediction, разделитель «;», все 151 строка)
```

Аудит: `python scripts/oracle_audit.py` — подтверждает, что `test/` и
`validate/` содержат одни и те же данные (метрики на них нельзя считать
независимыми), и умеет скорить произвольные предсказания:
`--predictions FILE` (apple-to-apple на общей выборке).

Ключевое требование к шагам 1 и 3: они должны вызывать тот же код, что
работает в онлайне. Иначе офлайн-метрика ничего не говорит о качестве
прогноза на живом потоке.

Тот же конвейер есть в `make`, одной командой и без расхождений с
`ML_FEATURES`:

```
make ml-replay-frames   # шаги 1 и 3: JSONL-кадры из Go-реплея
make ml-datasets        # predictor.dataset → dataset_{train,test,validate}.parquet
make ml-train           # predictor.train --features "$(ML_FEATURES)" → model_v1online.json
make ml-train-late      # predictor.late → model_v1online_late.json
```

`ML_FEATURES` — признаки, которые Go реально отдаёт в кадре. Обучение без
этого флага даёт модель на 38 колонках, 20 из которых в кадре отсутствуют:
MLClient отвергнет её при старте, и `make dev` молча уйдёт в baseline. Подробнее
— в `docs/architecture.md`, §4.5.

## 5. Что происходит при отказах

| Что сломалось | Что видит диспетчер | Как чинится |
|---|---|---|
| Эмулятор выключен | пустая карта, баннер «поток не поступает» | авто-старт `python scripts/emu_native.py serve` + `config` |
| NDTP-обрыв по одному ТС | ТС серая, иконка «нет данных», последняя позиция | reconnect с backoff, буфер дозаполняется |
| Python ML упал | позиции идут, карточки помечены «прогноз устарел» | circuit breaker → `last_known` → fallback |
| Postgres недоступен | дашборд работает, прогнозы буферизуются в памяти | reconnect, догон при восстановлении |
| Модель не загрузилась | баннер «резервное правило» | `POST /model/reload` без рестарта |

Все деградации **видны на экране** и отражаются в `/metrics` — жюри может проверить,
выдернув кабель.

## 7. Суть одной фразой

Эмулятор шлёт бинарные пакеты → Go читает их и превращает в отклонение от графика,
скорость и время простоя → за 10–15 минут до целевой остановки отправляет признаки
в Python → модель возвращает прогноз и причину → диспетчер видит красную точку на карте
за секунду до того, как автобус опоздает.
