Матрица built against `Предиктор_изменений_в_графике_движения_городского_транспорта.pdf`
(текст извлечён в `/tmp/opencode/tz.txt`). Дата проверки: 27 сентября 2026.

Замеры в разделе «Критерий 5» сняты с живого стенда: эмулятор NDTP на `:9201`,
backend на `:9201`/`:8080`, дашборд на `:5173`, три ТС в потоке.

## Критерий 1. Точность ML-прогноза (0–6)

| Требование ТЗ | Реализация | Доказательство | Пробел |
|---------------|-----------|---------------|--------|
| Прогноз вероятности задержки 10–15 мин | `ml/src/predictor/late.py` — отдельная голова вероятности, `p_late` в ответе | `/metrics`: `transport_gateway_predictions_from_model_total` | — |
| Абсолютная ошибка времени отклонения | MAE-регрессия на дельту `target − cur_dev_s` | `docs/data-audit.md` | — |
| Баллы ≥ 0.70 (MAE ≤ 32.4 с) | не достигнуто | baseline `pred = cur_dev_s`: **MAE 88.72 с → score 0.18** | **валидного замера модели на validate нет** |

**Честная оценка:** заявленный README baseline 0.40 не воспроизводится на данных —
фактический baseline даёт 0.18, то есть 1 балл. Модель не отмерена на validate,
поэтому балл за критерий 1 сейчас не earned, а заявлен. Это главный риск сдачи:
до дедлайна 27 сентября 23:59 МСК нужен хотя бы один сабмит с измеренным MAE.

Пороги из `docs/architecture.md`: 6 баллов — MAE ≤ 32.4 с, 4 балла — MAE ≤ 54.1 с.

## Критерий 2. Горизонт 10–15 мин (0–4)

| Требование ТЗ | Реализация | Доказательство |
|---------------|-----------|---------------|
| Строго 10–15 мин до события | `MinHorizon=10m`, `MaxHorizon=15m` в расчёте цели | `backend/internal/horizon` |
| Нет «прогнозов задним числом» | цель выбирается только вперёд от текущего момента; `claim()` дедуплицирует по `(vehicle, target_stop_id)` | `docs/adr/0005-target-stop-rule.md` |
| Предполагаемое время опоздания и причина | карточка инцидента: `pred_delay_s`, `cause`, участок | live: 72 инцидента, `source=ml` |
| Горизонт на потоке, а не офлайн | backend+ML на живом эмуляторе, `p50 6.4 мс` | live `/metrics` |

Прогнозы стабильно формируются в окне T+10…15 мин, задним числом не
выдаются: цели выбираются сеткой вперёд, поэтому после наступления события
дубль не создаётся.

| Требование ТЗ | Реализация | Состояние |
|---------------|-----------|-----------|
| Чётко выделены ML-ядро и Backend, не монолит | `ml/src/predictor/serve.py` (HTTP-сервис модели) + `backend/` (Go, API/оркестрация) + `dashboard/` (BI) | выполнено |
| API работает, Swagger отвечает | `GET /openapi.yaml` → 200, `GET /swagger` → 200 | выполнено |
| Backend принимает и парсит NDTP, сопоставляет с расписанием, считает признаки | `backend/internal/ndtp`, `features`, `mapmatch`; признаки: текущее отклонение, средняя скорость сегмента, время простоя | выполнено |
| Связь модулей end-to-end: поток → прогноз → дашборд | проверено вживую на свежем клоне: 43/43 прогноза от модели, 0 от baseline-фолбэка, дашборд live по WS через nginx | выполнено |
| **Упаковка в Docker-контейнеры** | `docker-compose.yml`: `ml` (FastAPI+CatBoost), `backend` (Go, multi-stage alpine), `dashboard` (Vite build → nginx) + одноразовый `plan-init` и опциональный `feed` | выполнено |
| **Поднимается по одной инструкции (README)** | `docker compose --profile feed up -d --build` из свежего клона; проверено: образы собираются, healthcheck'и проходят, прогнозы потекли | выполнено |

Воспроизводимость с нуля подтверждена прогоном в чистом клоне (клон →
`--profile feed up -d --build` → приёмка): боевые артефакты модели
(`model_v1online*`, `metrics_v1online*`) лежат в git именно ради этого —
иначе COPY в `ml/Dockerfile` падает на чужой машине.

## Критерий 5. Производительность и надёжность (0–4)

| Требование ТЗ | Замер | Оценка |
|---------------|-------|--------|
| Latency инференса < 1–2 с на поток ТС | стенд 2 ч (4 ТС, docker): **p50 2.5 мс, p95 2.8 мс, p99 3.1 мс, max 3.2 мс** (166 замеров); свежий клон (43 замера): p50 2.5 / p99 6.5 мс. Само ML-ядро: p50 0.7 / p99 1.8 мс | выполнено с запасом ×300 к худшему краю ТЗ |
| Пропускная способность без очередей | `transport_gateway_prediction_queue_depth = 0` на обеих выборках | выполнено |
| Деградация при обрывах связи без падения | эмулятор и клиенты отключались и возвращались, сервер продолжал работать; `readyz → true` после реконнекта; обрыв ml — baseline-правило без падения конвейера | выполнено |
| Предсказуемый холодный старт Docker | измерено на чистом клоне: полная сборка+подъём укладываются в минуты (точный разброс зависит от кэша образов и сети); пересборка/перезапуск отдельных сервисов — < 1 мин, ml healthy через ~15 с после старта контейнера | выполнено |

Замеры сняты с `/metrics` живого стенда, окно 1024 замера
(`backend/internal/latency`). Перцентили из короткого окна (после рестарта
контейнера) не сопоставимы с долгим стендом — число замеров указано рядом.

## Дополнительные возможности

| Фича | Состояние |
|------|-----------|
| Map Matching с учётом специфики NDTP | **реализовано**: `backend/internal/mapmatch`, встроен в `features` |
| Ансамбль регрессор + классификатор | **реализовано** (v4): CatBoost-регрессия `delay` + парный CatBoost-классификатор P(опозд. ≥ 120 с) с топ-причинами; один проход матрицы на обе головы, паритет фич сверяется при загрузке |
| Раннее предупреждение с причиной | **реализовано**: `reason` в инциденте (правила §5.4), карточка на дашборде |
| Деградация без падения (circuit breaker + baseline) | **реализовано**: обрыв ML → `pred = cur_dev_s` с явной пометкой `source` |
| Что-if анализ (выпуск доп. ТС) | **не реализовано** |
| Оптимизация инференса (ONNX/TensorRT/квантование) | **не реализовано**: p50 инференции 0.7 мс и так на два порядка меньше бюджета ТЗ |
| Ансамбль с PyTorch temporal encoder | **не реализовано**: план v5, в стеке не заявляется |

**Расхождение с документацией исправлено:** `docs/architecture.md` (§2 стек,
§4 схема) больше не заявляет PyTorch/ONNX как текущее решение — там прямо
написано, что это план v5, а в реальном стеке CatBoost-регрессор + отдельный
CatBoost-классификатор P(late).
