# 0003. Состояние и хранение без PostgreSQL

- Статус: принято
- Дата: 2026-09-25

## Контекст

`docs/architecture.md:88` и `:206` объявляют PostgreSQL 16 обязательным
компонентом: планы, остановки, рейсы, прогнозы, инциденты, метрики,
materialized views для аналитики. В порту 5432 зарезервирован сервис, в
`.env.example` есть блок `POSTGRES_*`.

При чтении критериев оценивания из ТЗ обнаружилось, что требования к базе
данных нет ни в одном из пяти критериев. Проверяется следующее:

- критерий 1 — MAE по таблице прогона сабмитов, чистый CSV;
- критерий 2 — горизонт 10–15 минут на потоке;
- критерий 3 — три модуля в Docker, Swagger отвечает, Backend принимает
  NDTP, считает производные признаки, связь end-to-end;
- критерий 4 — карта, цвета риска, карточка инцидента, live-обновление;
- критерий 5 — latency, пропускная способность, деградация, холодный старт.

Единственное упоминание хранилища — «сохраняется и пойдёт на проверку
заключительная версия» про формы платформы, к нашей системе отношения не
имеющее.

При этом PostgreSQL в таком решении — не бесплатный: отдельный контейнер,
healthcheck, миграции `infra/postgres/init.sql`, драйвер `pgx` в `go.mod`,
схема таблиц и её эволюция. И он же является лишней точкой отказа в
критерии 5, где требуется предсказуемость холодного старта и деградация без
падения.

Объём данных при этом мал: 56 транспортных средств, 16 674 строки
расписания, 90 точек телеметрии в окне на транспортное средство. Хранить
нужно по существу last-known-state, кольцевые буферы и небольшое число
открытых инцидентов.

## Рассмотренные варианты

### 1. PostgreSQL по плану

Отклонено как обязательное, но не как запрещённое. Переносится в фазу,
следующую за закрытием всех пяти критериев, если жюри попросит историю
прогнозов.

Причина в приоритете, а не в качестве: добавление СУБД не даёт ни одного
балла, а съедает время, которое можно потратить на дашборд и на качество
модели.

### 2. In-memory состояние + JSONL для персистентности

Принято.

## Решение

Горячий контур (состояние транспортных средств, кольцевые буферы,
открытые инциденты, последние прогнозы) живёт в памяти процесса
`transportctl`. Всё, что нужно пережить перезапуск, пишется в JSONL
по Append-семантике — тем же приёмом, что уже применён в
`backend/internal/telemetry` для наблюдений.

Ключевые следствия:

- **деградация бесплатна.** Падение хранилища невозможно: его нет.
  Требование критерия 5 «переход на последнее известное состояние»
  выполняется по построению, а не обработкой ошибки;
- **восстановление.** При старте JSONL перечитывается в кольцевые буферы,
  поэтому перезапуск контейнера не очищает картину у диспетчера;
- **детерминированный холодный старт.** Нет миграций, нет ожидания
  готовности СУБД, нет отказа из-за недоступного тома;
- **масштабирование ограничено одним инстансом.** Это осознанный размен:
  `docs/architecture.md:92` уже выбрал in-process hub для broadcast в
  WebSocket, то есть единственный инстанс был допущением и раньше.
  PostgreSQL покупает себя ровно тем, что делает возможным шардирование, —
  а шардирование не требуется на 56 транспортных средствах.

Контракт развёртывания сохраняется: в Docker Compose по-прежнему
поднимается несколько контейнеров (NDTP ingest, gateway, ML-ядро,
дашборд), требование «три модуля» из критерия 3 выполнено.

## Последствия

Что становится лучше:

- ни одного пункта критериев не теряется, а срок сокращается;
- `go.mod` остаётся пустым (см. [ADR 0002](0002-transport-and-dependency-boundary.md));
- критерий 5 закрывается деградацией без написанного кода обработки ошибок;
- демо на жюри не зависит от того, успел ли подняться postgres.

Что становится хуже:

- **история прогнозов ограничена размером файла.** Для аналитики «как
  менялся риск за смену» нужен либо разбор JSONL, либо СУБД;
- несколько реплик gateway невозможны: broadcast работает в одном процессе.
  При росте нагрузки это упрётся, и решение — вынести hub в Redis Streams
  или NATS, что заметно дороже текущего;
- аналитические витрины и сложные запросы по истории недоступны;
- `infra/postgres/init.sql` из `docs/architecture.md:444` не появится — при
  возврате к плану его нужно будет написать с нуля, а не «раскомментировать».

Отдельно: `.env.example` содержит блок `POSTGRES_*` и `ML_MODEL_PATH`,
которые сейчас не читаются ни одной строкой кода. Блоки, не влияющие на
поведение, удаляются при написании `.env.example` под фактический запуск,
иначе инструкция для жюри будет вводить в заблуждение.
