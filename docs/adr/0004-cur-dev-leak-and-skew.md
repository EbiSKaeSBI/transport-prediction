# 0004. `cur_dev_s`: утечка в разданном признаке и train/serve skew

- Статус: принято
- Дата: 2026-09-25

## Контекст

`docs/dataset.md` предлагает собирать обучающую таблицу из
`labels/labels_train.csv` и телеметрии с ограничением `event_time ≤ T`, и
называет это «правилом честности (анти-утечка)». Тот же инвариант записан
в `features/v1.yaml` как `no_future_leak`, а `docs/architecture.md:126`
заявляет: «Ноль train/serve skew — главный технический аргумент на питче.
Go должен считать признаки и для онлайна, и для офлайна… Расхождение между
обучением и продакшеном исключается по построению».

При подготовке фазы 1 это утверждение проверялось на данных. Оно не
подтвердилось, причём по двум независимым причинам. Ниже — измерения,
воспроизводимые скриптом из раздела «Проверка».

## Находка 1. `cur_dev_s` — курсор по плановому времени, а не по факту

Правило честной сборки «теперь только то, что известно на момент `T`»
подразумевает, что отклонение берётся у последней остановки, **фактически
пройденной** к моменту `T`. Это правило восстанавливает лишь 45.47 %
значений на `labels_train.csv` и 46.46 % на `labels_test.csv`.

Правило, которым на самом деле построен признак, другое: берётся строка с
максимальным **`time_begin` ≤ T** — то есть последняя остановка, *запланированная*
к моменту `T`, — и её отклонение `time_fact_begin − time_begin`. Оно
восстанавливает **99.15 %** на `labels_test.csv` и **98.24 %** на
`labels_train.csv`. Остаток — случаи, где две строки расписания имеют
одинаковое `time_begin` (разворот на конечной), и порядок между ними в CSV
потерян.

Следствие: `time_fact_begin` опорной строки **может оказаться позже `T`**.
На `validate/points.csv` это верно для **64 точек из 146, то есть 43.8 %**.
Пример: `tr_id=122048`, `T=04:30`, `cur_dev_s = 163 с` — опорная остановка
запланирована на 04:28, а фактическое прибытие по ней 04:30:43, то есть
после момента прогноза.

Вывод: признак, который организаторы раздали как подсказку и который
`features/v1.yaml` помечает `nullable: false`, сам по себе заглядывает в
будущее примерно в половине точек. Инвариант `no_future_leak` в буквальной
формулировке недостижим на предоставленных данных.

## Находка 2. `time_fact_begin` — синтетическая величина, а не физическое прибытие

Детекция прибытия по телематрии (`speed == 0` в течение ≥ 10 с поблизости
координаты остановки) не воспроизводит фактические времена из расписания:
совпадение в пределах ±180 с — 64.7 %, медиана смещения **+22 с**, в пределах
±30 с попадает лишь 24.6 % строк. Проверка на `labels_test.csv`: если
вычислять `cur_dev_s` из телеметрии, а не брать выданный, получается 3 точных
совпадения из 333 и MAE 103 с.

Признаки того, что `time_fact_begin` сгенерировано, а не измерено: 15.5 %
строк имеют отклонение ровно 0; отклонение образует гладкую
AR-подобную последовательность вдоль рейса; по геометрии самой остановки
момент прибытия не восстанавливается.

Следствие: Go-пакет `stopdetect` в принципе не может вычислить `cur_dev_s`,
равный тому, что дан в раздаче. Утверждение «исключается по построению» не
верно — **train/serve skew реален и является свойством данных, а не
архитектуры**.

## Рассмотренные варианты

### 1. Обучить на выданном `cur_dev_s`

Принято. Это тот признак, по которому считается MAE в разделе Data Science,
и подменять его значит сознательно ухудшать измеримую величину.

### 2. Обучить на телеметрически полученном `cur_dev_s`

Отклонено. Skew исчезает, но признак становится иным и более слабым, а
значение MAE в сабмите ухудшается. Критерий 1 оценивается по CSV, а не по
живому потоку.

### 3. Две отдельные модели

Отклонено как удвоение работы ради дефекта раздачи, а не ради свойства
предметной области.

## Решение

Модель обучается на выданном `cur_dev_s`.

Онлайн-контур вычисляет своё отклонение через `stopdetect` и
`speed_seg_avg`/`dwell_*` по телеметрии. Расхождение между офлайн- и
онлайн-значениями **измеряется, а не скрывается**: величина попадает в
метрики Prometheus и на панель производительности дашборда, чтобы дефект
раздачи был виден.

Инвариант `no_future_leak` в `features/v1.yaml` переформулируется с «только
`event_time ≤ T`» на «производные признаки строятся только из телеметрии с
`event_time ≤ T`; `cur_dev_s` принимается как внешний вход и его утечка
зафиксирована в ADR 0004». Формулировка станет выполнимой и перестанет
обесцениваться.

Раскрывается жюри открыто: это сильная сторона разбора данных, а не
неприятный сюрприз. `docs/data-audit.md` уже описывает утечку фактического
расписания test-подборки; этот ADR добавляет вторую, в самих признаках.

## Последствия

Что становится лучше:

- инвариант честности становится проверяемым, а не декларативным;
- величина skew доступна как метрика, поэтому её нельзя случайно
  «оптимизировать», не заметив;
- у жюри появляется конкретный, проверяемый пример глубины разбора данных.

Что становится хуже:

- MAE, измеренный на офлайн-выгрузке, **не переносится** на живой поток
  напрямую. Валидация ML обязана идти по `labels_test.csv`, а через
  оракул — по validate, с явной оговоркой;
- обещание «нулевого skew по построению» из `docs/architecture.md:126`
  снимается, и на питче заменяется более скромным и более честным;
- `stopdetect` придётся калибровать по косвенным признакам (длительность
  простоя относительно профиля маршрута), а не по точному прибытию.

## Проверка

Все числа выше воспроизводятся так:

```python
# правило курсора. cursor = 'TB' — плановое время, 'TF' — фактическое.
import csv, calendar
from collections import defaultdict
from datetime import datetime

def rd(p):
    with open(p, newline='', encoding='utf-8') as f:
        return list(csv.DictReader(f))

def E(v):
    v = v.strip()
    if '.' in v:
        b, fr = v.split('.', 1)
        return calendar.timegm(datetime.fromisoformat(b).timetuple()) \
               + int((fr + '000000')[:6]) / 1e6
    return calendar.timegm(datetime.fromisoformat(v).timetuple())

rows = rd('train/schedule.csv')
for i, r in enumerate(rows):
    r['fid'] = i
    r['TB'] = E(r['time_begin'])
    r['TF'] = E(r['time_fact_begin'])
by_veh = defaultdict(list)
for r in rows:
    by_veh[r['tr_id']].append(r)

labels = rd('labels/labels_train.csv')
n = len(labels)

for cursor in ('TB', 'TF'):
    ok = 0
    for p in labels:
        T = E(p['T'])
        cand = [r for r in by_veh[p['tr_id']] if r[cursor] <= T]
        if not cand:
            ok += float(p['cur_dev_s']) == 0.0
            continue
        top = max(r[cursor] for r in cand)
        row = min([r for r in cand if r[cursor] == top], key=lambda r: r['fid'])
        ok += abs((row['TF'] - row['TB']) - float(p['cur_dev_s'])) < 1e-9
    print(f'cursor={cursor}: {ok}/{n} = {100 * ok / n:.2f} %')
```

Ожидаемый вывод: `TB` даёт 98.24 %, `TF` — 45.47 %. Скрипт добавляется в
`tests/test_phase0.py` как отдельный тест-инвариант, чтобы правка раздачи
или смена генератора немедленно ломала сборку.

## Реализация в Go (зафиксировано 2026-09-25)

Онлайн-значение считает `internal/features`: `cur_dev_s` — это отклонение
последней остановки, у которой **и плановое, и фактическое время уже прошли
к `T`**. Строгое условие по факту — не перестраховка, а прямое следствие
Находки 1: если брать строку с максимальным `time_begin ≤ T` и не проверять
`time_fact_begin`, Go воспроизведёт утечку организаторов, и инвариант
`no_future_leak` перестанет быть инвариантом.

Измерение на `labels_test.csv` командой
`transportctl replay --plan test/schedule.csv --traffic test/traffic.csv
--labels labels/labels_test.csv`:

| величина | значение |
|---|---|
| меток | 353 |
| кадров построено | 326 (27 отклонено как «цель позади») |
| цель совпала с эталоном | **326 из 326 (100 %)** |
| `cur_dev_s` совпал с эталоном | 160 из 291, среднее \|Δ\| = 22.4 с |
| меток, где эталон опирается на факт **после** `T` | 142 (**43.6 %**) |

Две строки в таблице отвечают на разные вопросы и обе обязательны.

Первую строку goal — 100 % — даёт то, что правило ADR 0005 воспроизводится
организаторами точно: окно `(T+10 мин, T+15 мин]`, при равенстве времени
меньший `tt_action_item_id`, и 27 точек, отброшенных как «цель позади».
Правило проверено, а не предположено.

Вторая строка фиксирует цену честности. Расхождение по `cur_dev_s` в 43.6 %
меток объяснено **целиком** утечкой в эталонной подсказке: совпадение
достигается ровно в остальных 56.4 %, где факт опорной остановки к `T` уже
наступил. Это измерение, а не оправдание: оно показывает, что онлайн-контур
систематически получает менее оптимистичную подсказку, чем обучался, и это
расхождение обязано оставаться в метриках, как и сказано в разделе
«Решение».
